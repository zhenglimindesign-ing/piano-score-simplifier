# Execution reference

Use Python 3.10+ and an isolated environment under `work/`. Install this skill's `requirements.txt` there. Run `preflight.py`, then `fetch_schema.py work/schema` when network access is permitted. The latter downloads pinned W3C files and checks SHA-256; it does not send scores. No schema means the schema gate is NOT_RUN.

Examples below are agent operations; users need only describe the desired musical change. Resolve script paths relative to the skill folder, quote paths, keep scratch under work/ and deliverables under outputs/. Use a new version for each output; never overwrite input or an existing result.

```sh
python scripts/score_pipeline.py run --input INPUT.musicxml --out outputs/NAME-v1 --hands 1:R,2:L --level L2 --schema-dir work/schema --audio
python scripts/score_pipeline.py run --input outputs/NAME-v1/score-v1.musicxml --previous outputs/NAME-v1 --purpose repair --plan work/plan-v2.json --out outputs/NAME-v2 --hands 1:R,2:L --schema-dir work/schema
python scripts/score_pipeline.py run --input outputs/NAME-v2/score-v2.musicxml --previous outputs/NAME-v2 --purpose revision --request "USER WORDS" --edit-scope 6 --plan work/plan-v3.json --out outputs/NAME-v3 --hands 1:R,2:L --schema-dir work/schema
python scripts/score_pipeline.py annotate --manifest outputs/NAME-v2/manifest.json --check page_inspection --status PASS --by agent --evidence "Viewed pages 1-2 ..."
```

Each `run` writes a new version directory: input copy (first version), MusicXML, readback-checked MIDI, PDF and every page image, QA, event map (input ID → output ID), `manifest.json` and a short bilingual `REPORT.md`. Use `--previous` for every later version; its MusicXML must be the new input. `--purpose repair` follows a failed version and is refused after two targeted repairs. `--purpose revision` records the user's literal words and an `--edit-scope`; changes outside it are refused. `score_tool.py` remains available for single steps.

Exit codes: 0 automated gates passed (still REVIEW_REQUIRED until reviews are recorded); 1 ERROR (malformed input, rejected plan, broken version chain, out-of-scope edit, third repair); 2 FAIL (a gate failed); 3 INCOMPLETE (a mandatory automated gate did not run, e.g. unsupported notation, missing schema or renderer). Failed runs keep their manifest and error; inputs and earlier versions are never modified. `--hands` is a deliberate arrangement declaration, not an inferred default. If hands cross, change staff or implement explicit event hand assignments first.

Plan shape: `{"input_sha256":"...","protected_ids":["P1:m1:n2"],"edits":[{"id":"P1:m1:n4","op":"octave","octaves":1,"reason":"..."}]}` plus optional `request`, `musical_losses`, `remaining_difficulties`, `source_map` and `final_barline`. IDs use the part ID, one-based measure position and one-based note element position in that exact input; grace notes count. Printed bar labels and `--edit-scope` differ: every `mN`/scope number is the one-based input measure position, regardless of printed `number` attributes, pickups or lettered bars. Map the user's printed bar to that position before editing and report both (e.g. printed bar 15 → position 16 after a pickup). Operations, each with a reason:

- `octave` (±1 or ±2) and `remove_chord_doubling` (same-onset pitch-class duplicate);
- `remove_chord_member`: any chord tone; removing the anchor moves the next member's pitch into the anchor element so beams, slurs and tuplets stay, and the event map records it;
- `rest`: one note without remaining chord members or slur endpoints becomes a rest of the same value;
- `remove_grace`: an explicit ornament omission, removing the grace's own slur pair;
- `realize_grace`: one plain grace before one principal on the same voice/staff, with explicit `steal="following"` and exact positive `pulse_quarters`. Write it on the beat, borrowing from the principal while retaining its original release. A principal starting a valid tie chain or an exact grace-to-principal slur pair is supported. Multiple/chordal graces, incoming ties, qualified timing, other protected notation or a separately edited principal are rejected. This is an explicit timing proposal, not inferred pre-beat or historical practice;
- `realize_arpeggio`: one untied 2–4-note chord on one voice/staff, with the same arpeggiation group on every member. Supply a complete unique `order` of member IDs and exact positive `pulse_quarters`, consistent with any up/down direction. Successive tied chord groups add one note per pulse; all releases stay at the original chord end. Qualified/missing marks, mixed voice/staff groups, other notation, ties, protected or separately edited members are rejected. The event map records repeated tied segments for each source member;
- `realize_ornament`: write out one plain, untied `mordent` or `inverted-mordent` as principal–neighbor–principal. Supply a spelled `neighbor` (`step`, integer `alter` -1/0/1, integer `octave`) and exact `pulse_quarters` such as `"1/8"`. The neighbor must be an adjacent diatonic letter a semitone/whole tone in the symbol's direction. A mark qualified only by `long="yes"` additionally requires integer `cycles` 2–8; write `2*cycles` alternating pulse notes and a final principal filling the original remaining duration. Such a long mark may start a valid tie chain: the starting sounding/visual tie moves to the final principal, preserving the unchanged continuation. Incoming ties, chords, tuplets, other qualifiers/notation and protected notes need separate treatment. Existing divisions must represent every value exactly. Rhythm/pitch interpretation is an explicit proposal, not inferred historical practice. The event map's `expansions` records all output IDs, and outer-voice/scope checks still apply;
- `remove_ornament` with a named `ornament` (e.g. `trill-mark`, `mordent`, `turn`), or `remove_arpeggio`: omit exactly one existing symbol, preserving pitch/duration, ties and other notation. Accidentally qualified ornaments require separately authored treatment. Every omission needs a reason and reported musical loss; it never proves ornament realization;
- `set_clef`: `P1:m1:c2` names the second existing `<clef>` in measure 1; set `sign` to G/F/C and integer `line` to 1–5. This repairs source/layout notation without changing pitch, staff or hand assignments; transposing clefs require a separate treatment;
- `remove_direction`: `P1:m9:d2` is the second `<direction>` in measure 9 (never a tempo/sound direction).

A tied note can change only together with its whole tie chain in the same plan and by the same operation. Never move a note below the bass or above the melody to pass a span check; prefer removing doublings and inner voices, and list each loss. A plan that changes the lowest or highest sounding pitch at any attack or release boundary, including complete silence, is refused unless an edit in that bar carries `"outer_voice": ["bass"]` or `["top"]` and its reason says why; the manifest lists every such change (`after: null` means silence). `annotate` accepts a passing `musical_review` only from a person. Protected and unexplained edits are rejected. There is no hidden automatic arranger or octave optimizer.

Explicit implicit-length measures use their actual duration without padding. Non-nested whole-measure repeats (total play count 1–32) and paired first/second endings retain written notation and have a checked performed route. QA records written and playback durations separately, checks ties/hands in performed order, and restores written tempo at repeat jumps. Mid-measure/nested repeats, other ending layouts and D.C./D.S./Coda remain NOT_RUN, as do unrealized ornaments, arpeggiation, tremolo, transposition, complex meters and cross-staff ties; the run is then INCOMPLETE. Explicit symbol omissions are recorded losses and must stay inside the edit scope even if timed pitches do not change. Do not hand-edit the XML outside a plan to make gates pass. If a treatment such as writing out a repeat is musically needed, propose it, then author it as new notation with a source map and run the same checks. When the internal MIDI cannot run, a MuseScore MIDI may appear as `midi-musescore-unverified`, a listening aid without readback.

Profiles seed-0.1: L1 span≤7 semitones/count≤2; L2≤9/count≤3; L3≤12/count≤4. Both are maximum finger-held simultaneous limits, ties included. Movement advisories use onset-group centroid displacement (>7/12/19 semitones), not validated fingering distance. Peak one-second onset-group thresholds >3/5/8 bind to encoded quarter-note tempo. These are experimental engineering targets. Report hard violations plus maximum/p95 movement and explicit tempo; do not translate them into official exam grades. Pedal duration is not used to shorten finger holds. Rhythmic/voicing/reading burdens need separate musical review.

For PDF, locate MuseScore in the current host. MuseScore 4 uses `[mscore, '-S', style, '-o', output.pdf, canonical.musicxml]` as an argument list. MuseScore 3 with a style first imports canonical XML into an engraving-only MSCX, reads its native format version, saves a matching style into another MSCX, then reloads that file for PDF export. This avoids MS3's style-version rejection and missing relayout after `-S`. Retain both native intermediates, the supplied/applied style hashes and every command's stdout/stderr. MSCX files never replace canonical MusicXML or feed the internal MIDI. The pipeline uses `assets/readable-a4.mss` unless `--style` names another; inspect real pages either way. Version the style with the score. Convert every page with `pdftoppm` and visually inspect title, clefs, accidentals, ties, tuplets, spacing and endings. Fix readability without shrinking notation to meet a page budget. PDF import/layout and page turns remain separate checks. macOS sandbox XPC/pasteboard launch errors need the host's local process permission, not a missing-dependency diagnosis.

The MIDI exporter uses one piano channel per voice, merges adjacent ties and verifies serialized pitch/onset/end events. It uses uniform velocity with explicit tempo and no pedal/rubato/dynamic interpretation. Optional MuseScore audio is exported from the canonical MusicXML, with its source hash and engine recorded. MuseScore may interpret fermatas, articulations and dynamics differently from the internal literal MIDI; do not claim matching playback timing. Audio decoding is not human listening. Keep human listening/playing as NOT_RUN until it actually happens.

For host acceptance, verify discovery, a natural-language request, preserved inputs, same sample outputs, actual PDF pages, download/open behavior, a follow-up revision, and a malformed/unsupported input. Repeat Chinese and English prompts before claiming bilingual behavioral support. Do not install or invoke another AI agent just to simulate a platform test without task authorization.

Since v0.2.0, `hand_coordination` is a separate required gate: simultaneous finger-held copies of a key assigned to different hands fail until the notation has an explicit playable realization. This includes staggered attacks while a note is held. Hand-to-hand transfer after release is allowed. Overlapping registers without a shared key remain advisory. MIDI serialization can succeed for a musically conflicting two-hand score, so inspect every gate. Historical v1 files remain unchanged; new checks may reject them.
